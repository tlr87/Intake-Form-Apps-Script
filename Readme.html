1. System Overview

The RD3 Tech enquiry system receives enquiries from the RD3 Tech website and processes the submitted information through Google Apps Script.

The system is designed to perform several jobs automatically:

  • Receive the website enquiry.
  • Store the submitted information in the Form Responses sheet.
  • Evaluate the submission for important keywords.
  • Identify urgent enquiries.
  • Identify enquiries requiring manual review.
  • Identify potential spam.
  • Send an internal administrator notification.
  • Send a confirmation email to the client.
  • Keep the client-facing email separate from internal evaluation information.
Design principle: The form is the source of truth for the client data. The Admin and Client templates should display the same submitted information in the same logical order.

2. How the System Works

1
Client submits form Website enquiry is submitted.
2
Submission processed Apps Script receives and evaluates the data.
3
Alerts evaluated Keywords determine review, spam, and urgency.
4
Emails sent Admin alert and client confirmation are generated.

The administrator email contains internal evaluation information such as review flags, spam flags, urgent flags, and the reasons those flags were triggered.

The client email is deliberately simpler. It confirms receipt of the enquiry and displays the submitted enquiry information without exposing internal spam or review logic.

3. Form Fields & Data Order

The current form data order is important. The Google Sheet, backend data object, Admin email, and Client email should remain aligned with this structure.

# Form Field Purpose
1 Timestamp Time the enquiry was submitted.
2 Name Client name.
3 Email Client email address.
4 Phone Client telephone number.
5 Address / Location Client location or service address.
6 Preferred Contact Preferred communication method.
7 Have You Used RD3 Tech Before? Existing-client relationship information.
8 I am contacting RD3 Tech as Client category, such as Home user, Small business, or Community organisation.
9 What sounds like your situation? High-level description of the client's situation.
10 What's happening and what would you like to achieve? Detailed description of the problem and desired outcome.
11 How Soon Do You Need Help? Client timeframe or urgency.
Important: Do not casually rename or reorder these fields. If a field name changes, the backend, email templates, keyword evaluation, and documentation may also need to be updated.

4. Admin & Client Email Templates

Admin Email

The Admin email is the internal notification sent to RD3 Tech. It contains the complete enquiry data plus internal evaluation information.

The Admin template should display every field supplied by the form.

Client Email

The Client email confirms that the enquiry has been received. It should also display the submitted form information so the client can confirm that their details were received correctly.

Template rule: If a new field is added to the form, update both the Admin and Client templates. Do not update only one of them.

Current client information sequence

  1. Name
  2. Email
  3. Phone
  4. Address / Location
  5. Preferred Contact
  6. Have You Used RD3 Tech Before?
  7. I am contacting RD3 Tech as
  8. What sounds like your situation?
  9. What's happening and what would you like to achieve?
  10. How Soon Do You Need Help?

5. Alerts & Alert Types

The alert system evaluates the enquiry and can apply one or more internal flags.

Alert Meaning Admin Display Client Display
NEW INQUIRY No special alert condition was detected. Yes No
REVIEW REQUIRED The submission contains content requiring manual review. Yes No
URGENT INQUIRY The enquiry contains an urgent timeframe or urgent request. Yes No
SPAM DETECTED The submission matches spam or blocking rules. Yes No

More than one alert may be active at the same time. For example, an enquiry can be both REVIEW REQUIRED and URGENT INQUIRY.

6. Keyword Filtering

Keyword filtering allows the system to recognise potentially important content without requiring every enquiry to be manually reviewed.

Keyword categories

Category Purpose Typical Result
Review Keywords Words or phrases that indicate the enquiry may require human assessment. REVIEW REQUIRED
Urgent Keywords Words or phrases indicating the client needs assistance quickly. URGENT INQUIRY
Spam Keywords Words, phrases, or patterns commonly associated with unwanted submissions. SPAM DETECTED

Example

A client might submit: 

TV aerial needs tuning nintendo broken

If the configured review keyword list contains terms such as tv, tv aerial, tuned, or nintendo, the submission can be flagged for review.

If the client also selects an urgent timeframe such as As soon as possible, the urgent evaluation can independently trigger an urgent alert.

Important: Keyword matching should be conservative. Adding too many broad keywords can create false positives and cause ordinary enquiries to be unnecessarily flagged.

7. Keyword Taxonomy Editor

The Keyword Taxonomy Editor is the management interface used to maintain the classification rules without manually editing every part of the application.

What the editor controls

  • Spam keywords.
  • Urgent keywords.
  • Manual review keywords.
  • Keyword groups and classifications.
  • Rules used by the evaluation system.

Recommended workflow

  1. Open the Keyword Taxonomy Editor.
  2. Identify the appropriate category.
  3. Add the keyword or phrase only to the category that matches its intended purpose.
  4. Save the configuration.
  5. Submit a controlled test enquiry.
  6. Confirm that the expected alert appears in the Admin email.
  7. Confirm that internal evaluation details are not exposed to the Client email.
Do not use the taxonomy as a general keyword dump. Each keyword should have a reason for existing. Poorly designed keyword lists can cause excessive review alerts, false spam detections, or unnecessary urgent notifications.

8. How to Modify the System

Adding a new form field

  1. Add the field to the website form.
  2. Confirm the exact field name.
  3. Update the Form Responses header/order.
  4. Update the backend submission mapping.
  5. Update the Admin email template.
  6. Update the Client email template.
  7. Update any keyword or alert rules that should evaluate the new field.
  8. Update this documentation.
  9. Run a complete test submission.

Changing an existing field

Treat a field-name change as a system change, not simply a visual form change. 

Form field
   ↓
Submission data
   ↓
Google Sheet
   ↓
Backend mapping
   ↓
Keyword evaluation
   ↓
Admin template
   ↓
Client template

All relevant stages need to understand the new name.

Changing email appearance

Visual changes to the email templates are generally lower risk than changing the underlying field mapping. Keep the existing data-resolution logic intact unless there is a specific reason to change it.

9. Testing

Always test the complete workflow after a meaningful change.

Basic test

  1. Submit the form using controlled test information.
  2. Confirm the submission appears in Form Responses.
  3. Confirm the Admin email arrives.
  4. Confirm the Client confirmation arrives.
  5. Check that every field is displayed correctly.
  6. Check that field order matches the form.

Alert test

Test each alert independently where practical.

  • Normal submission → no special alert.
  • Review keyword → REVIEW REQUIRED.
  • Urgent request/timeframe → URGENT INQUIRY.
  • Spam test phrase → SPAM DETECTED.
  • Combined test → multiple flags where appropriate.
Testing reminder: Test submissions should not be allowed to become permanent production data. Before final launch, ensure the production Form Responses sheet is clean.

10. Deployment

When the system is ready for production, use a controlled deployment process.

  1. Finish and freeze the website form.
  2. Finish and freeze the Admin template.
  3. Finish and freeze the Client template.
  4. Confirm the keyword taxonomy.
  5. Run final controlled tests.
  6. Remove test data from the production response sheet.
  7. Ensure the production Form Responses sheet is correctly linked to the form.
  8. Confirm the header row is correct.
  9. Deploy the final Apps Script version.
  10. Perform one final live test.
Production goal: The first genuine customer submission should be the first meaningful production record in the clean Form Responses sheet.

11. Form Responses Sheet

The Form Responses sheet is generated and managed by the Google Form integration. It should not be treated like an ordinary manually maintained spreadsheet.

Important behaviour

When a Google Form is linked to a response destination, Google may create a replacement sheet such as Form Responses 2 or Form Responses 3.

This can happen when a response sheet is deleted or a form is reconnected to a spreadsheet.

Production reset procedure: If the response sheet has become contaminated with test data, disconnecting and reconnecting the form can be safer than trying to manually destroy all rows.

Recommended clean-reset process

  1. Confirm the form is no longer receiving live production submissions.
  2. Disconnect the existing response destination if required.
  3. Reconnect the form to the intended spreadsheet.
  4. Allow Google to create the new response sheet.
  5. Confirm the new sheet starts with the correct header row.
  6. Remove or rename obsolete response sheets only after the new connection has been confirmed.
  7. Confirm the production sheet is named Form Responses where the application expects that exact name.
  8. Submit a controlled test.
  9. Confirm the test reaches both email templates.

12. Troubleshooting

Admin email is missing a field

  1. Check the form field name.
  2. Check the backend property name.
  3. Check the Admin template resolver.
  4. Check whether the field is actually present in the submission object.
  5. Run a new test submission.

Client email is missing a field

Compare the Client template against the Admin template and the Form Responses header order.

Wrong value appears under a field

This normally indicates a mapping problem rather than an HTML formatting problem. Check the backend field mapping before changing the template.

Unexpected REVIEW REQUIRED alert

Check the Review keyword taxonomy and identify exactly which keyword caused the match.

Unexpected SPAM DETECTED alert

Check the spam taxonomy and the submission text. Avoid simply deleting the alert logic; first determine whether the keyword itself is too broad.

Urgent alert appears unexpectedly

Check the urgent keyword list and the timeframe field.

Form Responses starts at an unexpected row

Check whether the sheet contains previous test submissions or whether Google created a replacement response sheet after the form was reconnected.

13. Important Maintenance Rules

Rule 1 — Do not change the form casually. Once the production form is stable, avoid unnecessary field-name changes or reordering.
Rule 2 — The form is the source of truth. The Admin and Client templates should follow the form data rather than inventing a separate data structure.
Rule 3 — Keep internal logic internal. Review reasons, spam reasoning, keyword matches, and internal execution guidance belong in the Admin email, not the Client email.
Rule 4 — Test taxonomy changes. Every keyword change should be tested to make sure it produces the intended alert and does not create unnecessary false positives.
Rule 5 — Keep production data clean. Before final launch, remove test submissions or establish a clean production response sheet.
Rule 6 — Make one logical change at a time. When troubleshooting, avoid changing the form, backend, taxonomy, and email templates simultaneously. Otherwise it becomes difficult to identify what caused the problem.
